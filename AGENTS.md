- Certificate AI checks and blockchain proofs run in authenticated server functions (src/lib/certificates.functions.ts) so files are read with the caller's permissions and the AI key stays server-side.
- Blockchain proofs use a hash-chained ledger table plus keyless OpenTimestamps (Bitcoin) anchoring; no wallet or tokens to manage.
- Identity and listing decisions use authorized transactional database functions and triggers so verification, profile status, notifications, and audit records stay consistent.
- Private review evidence uses short-lived signed links with the caller's storage permissions.
- Content pages share app-specific metadata through pageMeta to keep the brand consistent.
- The root owns the single auth-state subscription; identity changes revalidate routes and role loads ignore stale sessions to prevent access-state races.
- Buyer/seller profiles share editable public profile fields; privileges live only in user_roles and only the administrator-only manage_account_role operation may change them, preserving audit records and administrator access.
- The accounts server functions authorize through the caller's has_role before loading privileged auth account data; profile editing never updates roles or verification fields.
- Listing review history fires on every actual verification-status transition, including transitions caused by BEFORE triggers on certificate edits, so invalidations cannot lose their audit or notification records.
- Administrator privileges require a multi-factor (aal2) session: has_role ignores the caller's own admin role otherwise, and the admin console shows an authenticator-app gate, so role changes and private documents stay protected even if a password leaks.
- Password recovery uses public pages and the root-owned recovery auth event; only a validated recovery session may submit a new password, existing TOTP factors must be verified before updates, and recovery never changes roles or authenticator factors.
- Homepage icon links share HomeLink, and the navigation brand mark uses the favicon asset, so all account and content pages keep consistent home access.
- KIPI journal evidence and private certificate checks are separate from marketplace approval; bounded server processing preserves source passages and uncertain publication status rather than inferring legal ownership.
- Listing visibility is enforced by database read policies against per-listing expiry timestamps; approval and verified payments create periods transactionally, while owner read paths retain suspended listings.
- Daraja STK uses explicitly authorized direct server credentials; unsigned callbacks only trigger independent STK status queries, and locked payment application prevents duplicate periods and excludes test payments from live visibility.
- One authenticated daily maintenance job handles expiry reminders, official journal discovery and at most ten PDF pages; source failures retain previous evidence and database leases prevent concurrent processing.
